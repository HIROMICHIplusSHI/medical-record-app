# 電子カルテアプリ 要件定義書

**プロジェクト名**: フリーランス美容施術者向け電子カルテアプリ
**対象施術**: アートメイク（出張型フリーランス）
**作成日**: 2025-10-12
**ステータス**: Draft v1.0

---

## 1. プロジェクト概要

### 1.1 背景と目的

**背景:**
- フリーランスのアートメイク施術者は現在スプレッドシートで顧客・施術情報を管理
- コスト入力の手動作業、請求書作成の非効率性が課題
- 患者情報を含むため、適切なセキュリティレベルが必要

**目的:**
1. **業務効率化**: コスト選択のテンプレート化、請求書の自動生成
2. **学習目標**: Ruby/Rails + TDD による問題解決プロセスの実践
3. **実用性**: 実際のフリーランス施術者が日常業務で使用可能なレベル
4. **ポートフォリオ**: 問題発見から解決までの一連のプロセスを可視化

### 1.2 主要ユーザー

**プライマリユーザー:**
- フリーランスのアートメイク施術者（元看護師）
- 出張型（クリニック・病院への派遣）
- 単一ユーザーを想定（将来的に複数ユーザー対応可能な設計）

**エンドユーザー（間接）:**
- 患者（施術を受ける個人）
- 施術場所（クリニック・病院）※請求先

## 2. 解決すべき課題

### 2.1 現状の問題点

| 問題 | 現状 | 影響 |
|------|------|------|
| コスト入力の手間 | 毎回手動で金額入力 | 時間のロス、入力ミスのリスク |
| 請求書作成 | 月末にスプレッドシートから手動集計 | 作業時間、ミスのリスク |
| 売上管理 | 自分で集計・計算 | 確定申告の準備が大変 |
| 患者情報管理 | スプレッドシートで管理 | 検索性が低い、セキュリティ懸念 |
| 施術履歴の追跡 | シートを遡る必要がある | 過去の情報を探すのに時間がかかる |

### 2.2 期待される効果

| 効果 | 指標 |
|------|------|
| コスト入力時間の削減 | 1施術あたり3-5分削減 |
| 請求書作成時間の削減 | 月末作業を30分以内に |
| 売上把握の迅速化 | リアルタイムでダッシュボード確認 |
| 患者情報の検索性向上 | 施術場所・日付でフィルタリング可能 |
| データの安全性向上 | 認証・暗号化によるセキュリティ確保 |

## 3. 機能要件

### 3.1 MVP機能（Phase 1）

#### 3.1.1 認証機能
- **ユーザー登録・ログイン**
  - メール/パスワードによる通常認証（Devise）
  - Google OAuth によるソーシャルログイン
  - パスワードリセット機能
  - セッション管理

#### 3.1.2 施術場所管理
- **CRUD操作**
  - 施術場所の登録・編集・削除・一覧表示
- **データ項目**
  - 施術場所名（必須）
  - 住所
  - 連絡先（電話番号、メールアドレス）
  - 備考欄
  - 登録日時、更新日時

#### 3.1.3 患者管理
- **CRUD操作**
  - 患者の登録・編集・削除・一覧表示
- **データ項目**
  - 患者名（必須）
  - 生年月日
  - 性別
  - 連絡先（電話番号、メールアドレス）
  - アレルギー情報
  - 既往歴
  - 備考欄
  - 登録日時、更新日時
- **関連付け**
  - 複数の施術場所で施術を受ける可能性に対応（多対多関係）

#### 3.1.4 コストシート管理（テンプレート機能）
- **CRUD操作**
  - コスト項目の登録・編集・削除・一覧表示
- **データ項目**
  - 項目名（例：眉毛アートメイク 2D、麻酔代）
  - 標準価格
  - カテゴリ（任意：施術、薬剤、消耗品など）
  - 説明文
- **機能**
  - テンプレートとして保存・再利用
  - カルテ作成時に選択可能
  - 個別に金額調整可能（モニター価格、施術回数による割引対応）

#### 3.1.5 カルテ管理（施術記録）
- **CRUD操作**
  - カルテの作成・編集・削除・一覧表示・詳細表示
- **データ項目**
  - 患者選択（必須）
  - 施術場所選択（必須）
  - 施術日（必須）
  - 施術内容（テキストエリア）
  - カウンセリング内容（テキストエリア）
  - 写真添付（Before/After、最大5枚程度）
  - コスト項目（複数選択可能、金額個別調整可能）
  - 合計金額（自動計算）
  - カスタムタグ（施術場所、施術内容などでのフィルタリング用）
  - 登録日時、更新日時
- **機能**
  - コストシートからの選択・追加
  - 手動でのコスト項目追加
  - 金額の個別調整
  - 写真のアップロード・削除
  - プレビュー表示

#### 3.1.6 検索・フィルタリング機能
- **検索条件**
  - 患者名（部分一致）
  - 施術場所（プルダウン選択）
  - 施術日（期間指定）
  - 施術内容（キーワード検索）
  - カスタムタグ（複数選択）
- **ソート機能**
  - 施術日（昇順・降順）
  - 登録日時（昇順・降順）
  - 金額（昇順・降順）

### 3.2 Phase 2 機能（早期追加）

#### 3.2.1 売上管理ダッシュボード
- **表示項目**
  - 月次売上（当月、前月）
  - 年次売上（当年、前年）
  - 施術場所別売上（月次・年次）
  - 施術内容別売上
  - 月別推移グラフ
- **集計機能**
  - カルテデータからの自動集計
  - 期間指定での集計
  - CSV/PDF エクスポート（確定申告用）

#### 3.2.2 請求書自動生成
- **生成機能**
  - 施術場所 × 月 での自動集計
  - 請求書テンプレートへの自動反映
  - PDF出力機能
  - プレビュー機能
- **データ項目**
  - 請求先（施術場所情報）
  - 請求期間
  - 施術一覧（日付、患者名、施術内容、金額）
  - 合計金額
  - 振込先情報
  - 発行日、請求書番号（自動採番）
- **管理機能**
  - 請求書の一覧・検索
  - 請求書の再発行
  - 送付済みフラグ管理

#### 3.2.3 月次総合売上表（確定申告用）
- **表示項目**
  - 月ごとの総売上
  - 施術場所別の内訳
  - 年間合計
- **エクスポート機能**
  - PDF出力
  - CSV出力（会計ソフト連携用）

### 3.3 Phase 3 機能（拡張機能）

#### 3.3.1 カスタムタグ機能の拡張
- ユーザー定義のタグカテゴリ作成
- タグのプリセット管理

#### 3.3.2 データエクスポート
- 全データのCSV/Excelエクスポート
- バックアップ機能

#### 3.3.3 レポート機能
- 施術統計レポート
- 顧客リピート率分析

## 4. 非機能要件

### 4.1 セキュリティ要件

**レベル**: 実用レベル（個人情報保護法準拠）

| 項目 | 要件 | 実装方法 |
|------|------|----------|
| 認証 | 安全なパスワード管理 | Devise（bcrypt暗号化） |
| 通信 | HTTPS強制 | Production環境で必須 |
| セッション | セキュアなセッション管理 | Rails標準のセッション + Secure Cookie |
| ファイル | 画像の安全なアップロード | Active Storage + S3 |
| アクセス制御 | 認証済みユーザーのみアクセス | before_action :authenticate_user! |
| データ保護 | 個人情報の暗号化 | 必要に応じてattr_encrypted使用 |

### 4.2 パフォーマンス要件

| 項目 | 目標値 |
|------|--------|
| ページ読み込み時間 | 2秒以内（平均） |
| 検索レスポンス | 1秒以内 |
| PDF生成時間 | 3秒以内 |
| 画像アップロード | 5秒以内（1枚あたり） |

### 4.3 可用性要件

| 項目 | 目標値 |
|------|--------|
| 稼働率 | 99%以上（月間） |
| バックアップ | 日次自動バックアップ |
| 復旧時間 | 24時間以内 |

### 4.4 ユーザビリティ要件

- **直感的なUI**: 特別な学習なしに操作可能
- **レスポンシブデザイン**: PC・タブレット・スマートフォン対応
- **操作フィードバック**: 保存・削除時の成功/エラーメッセージ
- **データ保護**: 誤削除防止の確認ダイアログ

### 4.5 保守性要件

- **コードカバレッジ**: 80%以上（RSpec）
- **ドキュメント**: README、セットアップ手順、API仕様
- **コーディング規約**: RuboCop準拠

## 6. データモデル概要

### 6.1 主要エンティティ

| エンティティ | 説明 |
|-------------|------|
| User | 施術者（ログインユーザー） |
| Facility | 施術場所（クリニック・病院） |
| Patient | 患者 |
| MedicalRecord | カルテ（施術記録） |
| CostSheet | コストシートテンプレート |
| CostItem | カルテ内のコスト項目 |
| Invoice | 請求書 |
| Tag | カスタムタグ |

### 6.2 主要な関連

- User has_many MedicalRecords
- Patient has_many MedicalRecords（複数の施術場所で受診可能）
- Facility has_many MedicalRecords（請求先として）
- MedicalRecord belongs_to Patient, Facility
- MedicalRecord has_many CostItems
- CostItem references CostSheet（テンプレート）
- Invoice belongs_to Facility（請求先）
- Invoice has_many MedicalRecords（請求対象の施術）

詳細なER図は別ドキュメント（`02_data_model.md`）を参照。

## 8. 開発方針

### 8.1 開発手法

- **TDD（Test-Driven Development）**: RSpecによるテストファースト開発
- **アジャイル**: 小さな機能単位で実装・テスト・フィードバック
- **Git Flow**: 機能ごとにブランチを切って開発

### 8.2 テスト戦略

| テストレベル | ツール | カバレッジ目標 |
|-------------|--------|---------------|
| モデルテスト | RSpec | 90%以上 |
| コントローラテスト | RSpec | 80%以上 |
| 統合テスト | Capybara | 主要機能100% |
| システムテスト | Capybara + JavaScript | クリティカルパス100% |

### 8.3 コーディング規約

- **Ruby Style Guide**: RuboCop準拠
- **コメント**: 日本語OK（わかりやすさ優先）
- **命名規則**: Rails規約に従う

## 9. 制約事項

### 9.1 技術的制約

- Rails 7系を使用（学習目的）
- Hotwire/Turbo使用（SPAフレームワーク不使用）
- 単一ユーザー想定（マルチテナント非対応）

### 9.2 スコープ外

- モバイルアプリ（将来的にAPI化して対応可能）
- リアルタイム通知機能
- 多言語対応（日本語のみ）
- 複数施術者の管理
- 予約管理システム（現時点では不要）

### 9.3 前提条件

- 施術者がPCまたはタブレットを使用できる
- インターネット接続環境がある
- モダンなブラウザ（Chrome, Firefox, Safari, Edge最新版）
